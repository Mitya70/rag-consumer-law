# RAG-ассистент по законодательству о защите прав потребителей: сравнение поиска, промптов и числа контекстов

Воспроизводимый эксперимент на русском корпусе законов: какой поиск (BM25, TF-IDF, плотные эмбеддинги, гибрид, реранкер) и какой промпт дают лучшие ответы, и что вообще добавляет поиск по сравнению с ответом модели «из головы». Все цифры ниже взяты из файлов в `results/`.

## Задача

Справочный ассистент отвечает на вопросы потребителя («купил телефон, через неделю сломался, что делать») по тексту закона, а не по знаниям, которые модель получила при обучении. Нужно выбрать конфигурацию RAG-системы (разбиение на чанки, поиск, промпт, число контекстов) и честно измерить, что работает, на оценочном наборе с известными эталонами. Проект учебный и **не является юридической консультацией**.

## Данные

- **Корпус** (65 статей, 117 332 символа, загружен 2026-11-21 скриптом `src/fetch_corpus.py` из Викитеки): Закон РФ «О защите прав потребителей» № 2300-1 (51 статья; версия страницы от 2023-12-30) и ГК РФ ст. 492-505 о розничной купле-продаже (14 статей; версия страницы от 2025-08-30). Нормативные акты не охраняются авторским правом (ст. 1259 ГК РФ). Текст в Викитеке может отставать от действующей редакции. Подробности: [`data/README.md`](data/README.md).
- **Оценочный набор** [`data/eval_set.csv`](data/eval_set.csv): 72 вопроса, 3 исключены ручной проверкой, **в итоговом наборе 69 вопросов**:
  - `formal`: 52 вопроса (42 с ответом в корпусе и 10 вне корпуса для проверки отказа). Черновики вопросов и эталонов сгенерировала модель `am/nemotron-3-ultra-550b-a55b` по тексту статей, затем программный фильтр (цитата-основание должна дословно входить в статью, вопрос не ссылается на номер статьи, лексические дубликаты отброшены). Вопросы вне корпуса составлены ассистентом (LLM) без опоры на статьи, их список зафиксирован в `src/build_eval_set.py`; три из них вошли в ручную проверку автором проекта.
  - `colloquial`: 17 вопросов в бытовой речи, со сленгом и опечатками, с малым пересечением лексики со статьями; пять из них требуют двух статей (вторая эталонная статья в колонке `gold_article_id_2`). **Написаны ассистентом (LLM)**, а не автором проекта.
- **Ручная проверка** (`review/review_sample.md`, `review/human_verdicts.csv`): человек (автор проекта) просмотрел 20 из 72 вопросов. Принято 17 (15 как есть и 2 после правки автора: q68 и q71), исключено 3 (q27 и q34 как юридизированные или нереалистичные, q70 как дубликат q40). **Итоговый набор: 69 вопросов, из них 17 проверены человеком, 52 остаются черновиками LLM без ручной проверки.** Ревьюер отклонил 3 из 20 черновиков (15%), поэтому непроверенная часть, вероятно, содержит похожие недочёты. Исключённые строки не удалены из CSV (колонки `excluded`, `exclusion_reason`), но не входят ни в одну метрику.

После исключения: поиск оценивался на 59 вопросах с ответом (42 formal и 17 colloquial), генерация на 69 (дополнительно 10 вопросов вне корпуса).

## Подход

1. **Чанкинг** (`src/chunking.py`): `article` (статья целиком), `part` (пункты статьи, склеенные до 250 символов), `win500` и `win1000` (окна по символам с перекрытием 20%). К каждому чанку добавлен заголовок «ЗоЗПП, ст. 18. Название».
2. **Поисковики** (`src/retrievers.py`): собственный BM25 на грубых основах слов (обрезка до 5 букв); TF-IDF по символьным n-граммам (3-5); плотный поиск моделями `nemotron-3-embed-1b` («small») и `nemotron-3.5-embed-8b` («large») через OpenAI-совместимый API (`input_type` = `passage` для чанков и `query` для запросов: проверено, что векторы различаются); гибрид BM25 + плотный через RRF; реранк первых 20 кандидатов моделью `nemotron-3.5-rerank-8b`.
3. **Метрики поиска:** hit@k и MRR на уровне статьи (чанк попадает, если принадлежит эталонной статье; для вопросов с двумя эталонными статьями засчитывается любая) с 95%-м бутстрэп-интервалом по вопросам.
4. **Генерация** (`src/run_generation.py`): генератор `am/nemotron-3-nano-omni-30b-a3b-reasoning` (бесплатная модель среднего размера с рассуждениями), температура 0.0, **k = 3 контекста**. Два лучших по поиску конфигурации (лучшая по hit@3 и MRR: `part` + плотный large + реранк; лучшая бесплатная без API: `win500` + TF-IDF) × три промпта (`naive`, `strict`, `strict_fewshot`) + контроль без поиска (тот же генератор отвечает на вопросы без подставленных фрагментов закона, опираясь только на знания, полученные при обучении). Тексты промптов: [`docs/prompts.md`](docs/prompts.md).
5. **Оценка ответов** по явной рубрике (correctness 0-2 относительно эталона, faithful: все ли утверждения подтверждены фрагментами, abstained: отказ отвечать; рубрика в `src/prompts.py`), температура судей 0.0:
   - `j1` = `ag/gemini-3-flash` (основной);
   - `j2` = `am/laguna-xs-2.1` (другое семейство, без рассуждений);
   - `j3` = `am/nemotron-3-ultra-550b-a55b` (кросс-проверка только на ответах на 17 проверенных вопросов лучшей конфигурации и контроле без поиска, 68 ответов).

   **Основной судья был заменён в ходе работы:** сначала им была `nemotron-3-ultra` (около 30 с на вызов, одного семейства с генератором), затем `j1` стал `ag/gemini-3-flash` (около 2 с на вызов, другое семейство); `nemotron-3-ultra` осталась кросс-проверкой на проверенном подмножестве. Ни один результат старого судьи в таблицах не используется.
6. Дополнительная метрика без LLM: `cites_gold`, упомянута ли в ответе эталонная статья («ст. 18»).

## Выводы

1. **Формальные вопросы не разделяют методы поиска, разговорные разделяют.** Вопросы, составленные по тексту статей, делят лексику с эталоном, и любая плотная модель упирается в потолок (hit@3 0.95-1.00). На разговорных вопросах BM25 и TF-IDF находят эталонную статью среди первых трёх только в 29% случаев, плотный small в 88%, плотный large в 100%.
2. **Гибрид BM25 + плотный (RRF) хуже одного плотного поиска** (MRR на разговорных 0.451 и 0.615 против 0.774 и 0.971): слабый лексический ранжир портит слияние.
3. **Реранкер сильно помогает слабому поиску и не доказал пользы сильному.** BM25 + реранк поднимает MRR на разговорных с 0.230 до 0.618, но плотный large даёт 0.971 [0.912; 1.000] против 1.000 с реранком: интервалы пересекаются, на 17 вопросах различить нельзя.
4. **Поиск добавляет много сверх знаний самой модели.** Без поиска полностью верны 40-46% ответов по j1 (43-53% по j2), с лучшим поиском и промптом `naive` 95-97% (по обоим судьям). На разговорных вопросах разрыв меньше (без поиска 0.588 / 0.765 против 1.000): модель знает закон частично, но на формальных вопросах и при отказах она чаще ошибается, а её ответы примерно втрое длиннее, чем у `naive` с поиском. Из 10 вопросов вне корпуса без поиска верно отказывается только 40-60%.
5. **Качество поиска определяет качество генерации.** При бесплатной конфигурации (TF-IDF) эталонная статья попадает в контекст у 75% вопросов (29% на разговорных) и верных ответов 44-71%, а строгие промпты дают 24-27% ложных отказов по j1: при строгом промпте модель честно отказывается, когда ответа в контексте нет.
6. **Промпт: `naive` точнее, `strict` честнее по источникам.** По обоим судьям `naive` ≥ `strict` > `strict_fewshot` по доле верных ответов (разница между naive и strict 5-10 пунктов, интервалы частично пересекаются). Зато strict называет эталонную статью в 97% ответов против 49% у naive. Strict-ответы короче (209 символов против 649), а эталоны на разговорных вопросах многокомпонентные, из-за чего краткость стоит полноты. Few-shot ухудшил результат относительно strict.
7. **k = 3 разумный компромисс.** k = 1 заметно хуже на разговорных вопросах по j1 (0.765 против 1.000), k = 5 не улучшает результат (1.000 / 1.000) при примерно 1.6-кратном росте числа токенов в промпте (836 → 1316). На всех вопросах судьи расходятся по направлению (j1: 0.881 → 0.966 → 0.949; j2: 0.966 → 0.949 → 0.983), поэтому различия между k = 3 и 5 в пределах шума.
8. **Температура 0.7 не дала доказуемого эффекта, а T = 0.0 не гарантирует повторяемости.** Разница между температурами (3-3.5 пункта) меньше разброса между прогонами; оценки отдельных вопросов менялись между прогонами и при T = 0.0 (6.8-18.6% вопросов в зависимости от судьи).
9. **Платная модель не нужна для качества ответа при хорошем поиске, но знает закон лучше и хуже отказывается.** С поиском обе модели дают 95-98% верных ответов; без поиска платная даёт 81-83% против 46-53% у бесплатной; зато верный отказ на вопросах вне корпуса у неё 20-30% против 80%, то есть она охотнее отвечает «от себя».

## Ограничения и что можно улучшить

- **Маленький и частично непроверенный набор.** 17 вопросов проверены человеком, 52 из 69 остаются черновиками LLM. Человек отклонил 3 из 20 просмотренных черновиков (15%), значит, в непроверенной части вероятны похожие недочёты. Формальные вопросы по тексту статей лёгкие и упираются в потолок; разговорные вопросы написал ассистент, видевший корпус, поэтому они могут быть ближе к статьям, чем реальные пользовательские.
- **Один эталон на вопрос.** Одни и те же факты встречаются в нескольких статьях (например, «10 лет» в ст. 7, 14 и 19); засчитывается только указанная эталонная статья (или одна из двух), поэтому поиск мог быть оценён строже, чем он есть.
- **Выбор генератора и судей.** Генератором намеренно выбрана бесплатная модель среднего размера с рассуждениями: более сильная модель маскировала бы ошибки поиска, но с хорошим поиском платная модель (раздел 6) даёт тот же результат. Судьи `j1` и `j2` из других семейств, чем генератор (Gemini и Laguna против Nemotron), но это разные модели с собственными смещениями, и они расходятся (kappa по faithful 0.40); `j3` из того же семейства, что и генератор, и она же писала черновики формальных вопросов, поэтому у кросс-проверки возможно смещение. Ручная сверка выполнена на 10 ответах ассистентом, а не автором проекта.
- **Недетерминизм API.** Проба температуры (`results/temperature_probe.csv`, 5 вопросов, по два вызова без кэша): при T = 0.0 одинаковыми оказались 2 ответа из 5, при T = 0.7 ни одного из 5; медианная разница числа токенов между повторами 64 против 100. Модель реагирует на температуру, но и при T = 0.0 результат не детерминирован, поэтому различия в несколько пунктов в таблицах находятся в пределах шума запусков. Три прогона на температуру (раздел 5) это подтвердили: оценка вопроса менялась между прогонами у 7-19% вопросов и при T = 0.0.
- **Корпус и модели.** Версия закона из Викитеки может отставать от действующей. Генератор, судьи, эмбеддинги и реранкер бесплатные и могут измениться. Локальные модели эмбеддингов (`multilingual-e5`, `bge-m3`) не запускались: PyPI и Hugging Face отдавали 1-14 КБ/с, поэтому бесплатными базовыми линиями служат BM25 и символьный TF-IDF.
- **Размер интервалов.** Бутстрэп-интервалы по 17-59 вопросам широкие (см. таблицы); при нулевом числе промахов интервал вырождается в точку.

## Что не выполнено / планы

- Абляция по температуре и сравнение с платным генератором выполнены (разделы 5 и 6). Не сделано: сравнение нескольких платных моделей, повтор абляции температуры на другом промпте и с большим числом прогонов (трёх мало, чтобы отличить эффект в 3 пункта от шума), измерение стоимости ответа.
- Проверка человеком остальных 52 вопросов; локальные эмбеддинги; больше разговорных вопросов, собранных не по тексту корпуса.

## Стек

Python 3.10+, numpy, pandas, scikit-learn (TF-IDF), requests, BeautifulSoup и lxml (сбор корпуса), matplotlib, Jupyter. Модели вызываются через OpenAI-совместимый API (адрес и ключ в `.env`). Код и черновики формальных вопросов подготовлены с помощью LLM-ассистентов как инструмента разработки; метрики получены запуском скриптов на реальных вызовах API, а часть вопросов и ручные метки проверены человеком, как описано выше.

## Как запустить

```bash
pip install -r requirements.txt
cp .env.example .env            # впишите OPENAI_API_KEY и модели; .env в git не попадает
cd src
python fetch_corpus.py          # корпус -> data/corpus.jsonl
python build_eval_set.py        # оценочный набор (черновики), разговорные вопросы, вердикты ревью
python run_retrieval.py         # поиск -> results/retrieval_*.csv
python run_generation.py        # генерация, оценка судьями, абляция по k -> results/generation_*.csv, k_ablation.csv
python judge_agreement.py       # согласие оценщиков и сверка с ручными метками
python make_notebook.py         # notebooks/results.ipynb
```

Все ответы API кэшируются в `.cache/` (в git не попадает), поэтому повторный запуск пропускает сделанное. Ключ нигде не печатается и не сохраняется в результатах. Структура: `data/` (корпус, оценочный набор), `src/` (код), `results/` (сырые результаты и сводки), `review/` (выборка для ручной проверки и вердикты `human_verdicts.csv`), `docs/prompts.md` (тексты промптов), `notebooks/results.ipynb` (таблицы и графики).
